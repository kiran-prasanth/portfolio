BS-089  ·  In Progress  ·  Epic

Automated design token sync pipeline — push Figma variable changes to client codebase via PR, no manual handoff

Epic High priority Sprint 11–12 Design Systems · Frontend · Integrations 13 pts
Problem Every time a designer updates a colour, spacing value, or typeface in Figma, a developer must manually diff the changes, update CSS/SCSS variables in the client's codebase, and push a commit — taking 30–90 minutes per update and introducing transcription errors across all active client retainers. At 6 concurrent design-system clients, this manual sync consumes approximately 8–12 developer hours per sprint. This epic scopes an automated pipeline that detects Figma variable changes, transforms tokens into code-ready output, and opens a versioned pull request — requiring only a developer review and merge.

Pipeline Overview

Figma Variables API→ Webhook trigger→ Token extraction→ Style Dictionary transform→ Diff & semver check→ GitHub PR (auto-opened)→ Dev review & merge

User Stories

As a designer at Brandshark,
I want my Figma variable changes to automatically propagate to the client's codebase as a pull request,
so that I can iterate on the design system without waiting for a developer or risking values being transcribed incorrectly.
As a developer reviewing the client's codebase,
I want the auto-generated PR to clearly show what changed, what type of change it is, and whether any tokens were renamed or removed,
so that I can confidently merge or flag breaking changes without reverse-engineering the Figma file.

Acceptance Criteria

  • When a designer publishes a Figma variable change in a monitored file, the pipeline triggers within 5 minutes. The designer does not need to do anything beyond the normal Figma publish action.
  • The extraction service reads all variables via the Figma Variables REST API and outputs a structured tokens.json following the W3C DTCG format, committed to a /tokens branch before transformation.
  • Style Dictionary transforms tokens.json into CSS custom properties (tokens.css), SCSS variables (tokens.scss), and a flat JS object (tokens.js). All three are included in the PR. Output format is configurable per client.
  • The pipeline performs a semantic version bump before opening the PR. Rules: patch for value changes; minor for new tokens added; major for any token renamed or deleted. PR title includes the bumped version and a one-line summary.
  • The auto-generated PR description includes a diff table: changed token names, old value, new value, and change type (updated / added / removed). Removed tokens are highlighted with a warning block.
  • If the pipeline detects a major version bump, it posts a Slack notification to #ds-alerts tagging the assigned developer before the PR is opened.
  • Each client has an isolated config at /config/{client-slug}.json specifying: Figma file ID, target repo, target branch, output formats, Slack channel, and per-token-group exclusions (tokens prefixed _draft are never exported).
  • If the pipeline fails at any stage, it logs a structured error to the internal monitoring dashboard and sends a Slack alert to #ds-pipeline-errors. It does not silently fail.

Edge Cases & Constraints

  • !Figma API rate limits: The Figma Variables API allows 1 request per second per token. Files with more than 500 tokens require request queuing with exponential back-off — not parallelised bursts — to avoid 429 errors mid-pipeline.
  • !Draft / WIP tokens: Any token beginning with _ or in a group marked [wip] must be excluded at the extraction step — not as a post-transform filter.
  • !Multi-mode tokens: Figma variable modes (light/dark, brand A/brand B) must be preserved in output. Output files named accordingly: tokens.light.css, tokens.dark.css.
  • !No open PR conflict: If a previous PR is still open and unmerged, do not open a second PR. Push new commits to the existing branch and update the PR description with the cumulative diff.
  • !GitHub permissions: The pipeline uses a Brandshark-managed GitHub App — not a personal access token — so access can be scoped per-repository and revoked per-client without rotating shared credentials.

Technical Notes (for devs)

Figma trigger: Use Figma's FILE_VERSION_UPDATE webhook event. Register per client file ID at onboarding. Payload includes file_key and timestamp — use to fetch variables via GET /v1/files/:file_key/variables/local.

Token transformation: Style Dictionary is the transform layer. Write a custom formatter for DTCG-to-CSS-custom-property output — Style Dictionary's built-in CSS formatter does not handle DTCG $value and $type structure natively. Keep the formatter as a standalone module for reuse in BS-094.

Diff logic: After transform, diff new tokens.json against the last-merged version stored in /tokens/.last-sync.json in the repo. Classify each delta programmatically — do not rely on Git diff for semantic classification.

PR auto-generation: Use GitHub REST API (POST /repos/{owner}/{repo}/pulls). PR body is templated in Markdown from the diff output. Assign to repo's default reviewer (set per client in config). Label with design-system and semver tier (breaking, minor, or patch).

Config schema: All client configs validated against a JSON Schema on pipeline boot. If malformed, pipeline refuses to run for that client and logs the validation error — no silent fallback to defaults.
