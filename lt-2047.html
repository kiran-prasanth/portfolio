Real-time delay alerts for fleet managers when shipment ETAs shift beyond threshold

Feature High priority Sprint 14 Notifications · Backend Estimate: 5 pts
Context Fleet managers currently discover shipment delays only when drivers call in or clients complain. There is no proactive system-triggered alert when a shipment's live ETA deviates significantly from the committed delivery window. This causes reactive scrambling, client trust erosion, and missed SLA documentation opportunities.

User Story

As a fleet manager,
I want to receive an automated alert when a shipment's estimated arrival time shifts by more than 30 minutes from the committed delivery window,
so that I can proactively inform the client, reassign resources if needed, and log the delay reason before the delivery window lapses.

Acceptance Criteria

  • When a shipment's live ETA (from GPS telemetry) deviates by ≥ 30 minutes from the committed delivery window, the system triggers an in-app notification and an email alert to the assigned fleet manager within 2 minutes of the threshold being crossed.
  • The alert includes: shipment ID, driver name, origin → destination route, committed ETA, current ETA, and estimated delay duration. No other fields are required in the initial alert.
  • If the ETA recovers (delay drops below 30 min), a single "ETA recovered" notification is sent. No further delay alerts fire for that shipment unless the threshold is crossed again after a 60-minute cool-down period.
  • The fleet manager can configure the delay threshold (default 30 min) per delivery zone from the Notification Settings panel. Valid range: 15–120 minutes, in 15-minute increments.
  • Alerts are not triggered for shipments already marked as "Delivered," "Cancelled," or "On Hold" in the system at the time of ETA recalculation.
  • In-app alerts appear in the existing Notification Center and increment the unread badge count. They are dismissible and persistent until manually cleared by the manager.

Edge Cases & Constraints

  • !GPS signal loss: If telemetry is unavailable for > 10 minutes, suppress ETA recalculation and do not fire delay alerts. Show a "Tracking unavailable" flag on the shipment card instead.
  • !Multiple delay events: Do not send duplicate alerts for the same shipment within the 60-minute cool-down window even if the ETA continues to slip. Aggregate slippage data silently until the cool-down resets.
  • !Manager not assigned: If no fleet manager is assigned to a shipment, route the alert to the team's default Ops email (configurable in Team Settings). Log this fallback in the audit trail.
  • !Night-shift quiet hours: Email alerts should respect the manager's quiet hours setting (if configured). In-app notifications should still fire and be visible on login.

Technical Notes (for devs)

ETA source: pull from shipment.live_eta field, updated every 5 min by the telematics service. Committed window is stored in shipment.committed_eta at booking time — treat this as immutable for alert calculations.

Threshold comparison: abs(live_eta - committed_eta) >= threshold_minutes * 60. Run this check on every ETA update event from the telematics queue.

Email template: use existing transactional email layout. Subject line format: [Delay Alert] #{shipment_id} — {route} — ETA now {new_eta}.

Notification storage: persist alerts in the notifications table with type = 'delay_alert' and shipment_id FK. Ensure alert records survive shipment status changes for audit purposes.
